How to add materials, reactions, tools, plants and buildings to Dwarf Fortress using Refinish Metal's module system.

#1What this system is

#The problem

Dwarf Fortress reads raw files once, when a world is generated. Materials and reactions added afterwards do not exist in that world. Adding content to an existing save means regenerating the world, and removing a mod from a save corrupts it.

#What RM does instead

Refinish Metal writes content directly into the game's memory at load time, after the world is already open, and sweeps it back out before the game saves. Nothing your module injects (materials, reactions, categories, tools, plants, building definitions) is written into the save.

That gives you two things raws cannot:

  • Content works on existing saves. No regeneration.
  • Nothing has to be decided at worldgen. Your module can read the loaded world and adapt to it.

#What this does not mean

A module cannot be fully uninstalled from a save. This is worth being precise about, because the distinction is easy to overstate.

Your module is still a DF mod. Once it is active for a world, DF records it in that save's mod list and keeps its info.txt, exactly as it does for RM itself. Delete the mod from disk and the save loses a mod it expects to find.

What RM's approach actually buys is that the injected content is not part of the save. That is what makes existing saves usable and what stops a half-removed mod from corrupting one. It is not the same as leaving no trace.

The realistic lifecycle is dormancy, not removal. A module that stops responding to RM's token call injects nothing, and the save continues to work without its materials. The mod entry stays. Design for that: assume a player may turn your content off, and make sure nothing you leave behind depends on it coming back.

#What you write

A module is one small Lua file and the JSON data files it points RM at: a materials file and a reactions file, plus, when you need them, a tools file, a plants file and a buildings file. Every JSON file goes in the module's data folder, and the PNG sheets they name go in an images folder inside data. You do not write engine code. You describe your content in a schema, and RM builds it.

#What this system is not for

RM adds content. It does not remove or rewrite content that already exists: if you need to change a vanilla material or delete a vanilla reaction, that still belongs in raw files. The one edit RM offers on existing materials is a reaction class given at run time and taken back before every save, through its material classes service (section 9, RM's services).

#How the pieces connect at runtime

  1. DF loads a world. DFHack runs every script in scripts_modinstalled/.
  2. Your Lua file registers a listener with RM's module engine (register_listener(name, callback, mod_id)) and returns immediately. Nothing else happens yet.
  3. RM starts up and broadcasts a token call to every registered listener. A listener that gave a mod_id is only called when that mod is active in the loaded world. A mod_id that matches no installed mod is called anyway, with a warning to correct it.
  4. Your listener responds with your data, either as file paths or as already parsed tables (section 8.1).
  5. RM validates the data one entry at a time. A bad material, reaction, category or tool is left out and named in the log, and the rest of your module still loads. The module is refused whole only when it cannot be identified or nothing valid is left (section 10).
  6. RM injects modules in dependency order, RM's own catalog forms first. For each module, in this order: tools, plants, materials, your on_materials_injected function if you returned one, buildings, categories, reactions.
  7. Once every module is in: reaction_products that name other modules' materials are resolved, saved jobs on module reactions are pointed back at their reactions, and each accepted module's start function runs, if it returned one. Civilization permissions are granted after that, in RM's own startup.
  8. Before every save, at a shutdown and at the map unload, RM runs your stop function if it ran your start, then sweeps everything back out. After a save it injects again and runs start again.

A refused module is never started: its start never runs, and the log says so under its name. That is why a module's scripts belong in start and never in the listener itself: the listener runs before validation, so a script started there keeps running for a module RM then refuses, and polls on through every save while the module's data is out of RAM. start and stop are optional.

Registration is deliberately cheap. Your listener is a callback that is stored and called later, once the world raws exist. That ordering is why you cannot read df.global.world at the top of your Lua file.

#The prefix

Every module owns a prefix, a string ending in an underscore. RM stamps it onto everything you inject.

You write RM creates
material key GOLDBRONZE inorganic MYMOD_GOLDBRONZE
reaction key MAKE_GOLDBRONZE reaction MYMOD_RXN_MAKE_GOLDBRONZE
category key ALLOYS category MYMOD_CAT_ALLOYS
tool key CRUCIBLE tool itemdef MYMOD_CRUCIBLE
plant key DYE_HOST plant MYMOD_DYE_HOST
building key KILNETTE building MYMOD_KILNETTE

The prefix is how RM tells your content apart from everyone else's, including during cleanup. Two rules follow from that:

  • No two modules may have overlapping prefixes. Not just identical ones. THISMOD_ overlaps THISMOD_TOO_, because a sweep for the first also selects the second, and one module's shutdown would delete the other's materials. RM refuses the overlap at registration.
  • REFINISH_STEEL_ is reserved for RM's own finishes, and RM's own content registers through the same engine under REFINISH_CORE_, REFINISH_BRICK_, REFINISH_DYE_ and the catalog prefixes (REFINISH_GRAVEL_ and the rest, section 9). The overlap rule keeps you off all of them. Do not start a prefix with REFINISH_.

Pick something specific. MYMOD_ is fine. METAL_ is asking for trouble.

#3Your first module

#Step 1: info.txt

Standard DF mod metadata. The [ID:...] value is the one that matters here, because your Lua file uses it to find your own folder on disk, and it is the mod_id your listener can pass so RM only calls it in worlds that have your mod.

[ID:my_module]
[NAME:My Module]
[DESCRIPTION:Adds a new alloy.]
[NUMERIC_VERSION:1]
[DISPLAYED_VERSION:1.0]
[EARLIEST_COMPATIBLE_NUMERIC_VERSION:1]
[EARLIEST_COMPATIBLE_DISPLAYED_VERSION:1.0]
[REQUIRES_ID:refinish_steel]
[STEAM_TITLE:My Module]
[STEAM_DESCRIPTION:Adds a new alloy.]

[REQUIRES_ID:refinish_steel] declares the dependency on Refinish Metal itself. Every module needs this line. Your Lua file does nothing but register a listener, so without RM there to call it, the mod loads and then sits inert with no way for the player to tell why. Declaring the dependency puts that in front of them instead.

#Step 2: the JSON files

Copy rm-module-materials-template.json and rm-module-reactions-template.json into data/. Rename them. Change the module block in both files to your own prefix, name, and version.

Tools, plants and buildings have templates of their own: rm-module-tools-template.json, rm-module-plants-template.json and rm-module-buildings-template.json. Each starts with a reference entry showing every field it accepts, annotated, then a short working example.

The module block:

Field Required Notes
prefix Yes Ends in an underscore. Must not contain REFINISH_STEEL_.
name Yes What the log calls your module.
version Yes A non-empty string.
depends_on No Prefixes of modules to inject before yours (section 9).
requires No RM catalog forms your module uses (section 9).

prefix, name and version are checked in the materials and the reactions file. The two prefixes must match, or RM refuses the module. The module's name and depends_on are read from the materials block first, then from the reactions block. requires is gathered from every file's block. A tools, plants or buildings file carries a module block too; a tools or buildings file can supply the prefix for a module that has no materials or reactions.

#Step 3: the Lua file

Copy rm-module-template.lua into scripts_modinstalled/, rename it, and set four values at the top:

local MODULE_ID      = "my_module"                   -- from info.txt
local MODULE_NAME    = "My Module"                   -- for log output
local MATERIALS_FILE = "my_module_materials.json"
local REACTIONS_FILE = "my_module_reactions.json"

That is the whole file. Everything below the configuration block is boilerplate you should not need to touch.

Use rm-module-template-advanced.lua instead if you need to inspect or edit your data before RM sees it, start helper scripts, or ship tools, plants or buildings. Section 8 covers when that applies.

#Step 4: preflight

preflight.py checks your JSON offline, without launching DF. It parses the type tables in refinish-module-types.lua rather than carrying its own copies, and it checks your files against the same rules as the engine's validator.

Put the script, the types file and your JSON in one folder and run it:

preflight.py
refinish-module-types.lua        copied from your RM install
my_module_materials.json
my_module_reactions.json

python3 preflight.py

It finds *_materials.json, *_reactions.json and *_reactions_*.json on its own, and the optional *_tools.json, *_plants.json and *_buildings.json. Pass paths explicitly if you keep them elsewhere:

python3 preflight.py path/to/mats.json path/to/rxns.json --tools path/to/tools.json --plants path/to/plants.json --buildings path/to/buildings.json --types path/to/types.lua

Several reactions files may be passed after the materials file.

Errors fail the run. Warnings do not. An error is something the validator refuses: in game that entry is left out, or the whole module when the error is in its module block. A warning is either something the script cannot verify offline, or something legal that is a known way to shoot yourself: a colour with no fallback, a reaction with no skill, an in_container reagent with nothing declaring it contains it, a to_container bag that is not preserved, a dye declared as an inorganic.

Warnings are grouped by kind with a count, because a large module can produce hundreds of the same one. --verbose prints them all. --strict makes them fail the run, which is useful in a build script.

Beyond the validator, it also cross-checks references the engine resolves silently: a mat_id carrying your prefix that no material declares, a category written as the bare key where the full ID is required, a PLANT_MAT: token naming a plant or material your plants file does not declare, and tools, buildings and the image files they name. Those resolve to nothing in game and produce content that quietly matches nothing, which is the worst failure mode to debug from inside DF.

One thing to know about nulls. If you use the runtime resolution pattern (section 8.4), write "mat_id": null explicitly rather than omitting the key. Preflight treats an explicit null as a deliberate sentinel and warns; it treats a missing key as a mistake and errors. That distinction is the only signal it has.

Re-copy refinish-module-types.lua from your RM install whenever RM updates. Preflight is only as current as that file.

#Step 5: test it

Enable the mod, load a save, and open RM's log panel. You are looking for a line naming your module in RM's startup output. If anything was left out or the module was refused, the message names the exact field.

Two things to know before you start iterating:

  • Restart fully between tests. Quit DF, clear the cache, relaunch. A partially reloaded script environment produces failures that have nothing to do with your change.
  • refinish-find and refinish-path are RM's diagnostic commands. Use them to confirm what actually landed in memory rather than assuming.

#4The materials file

A material is one inorganic: a metal, a stone, a gem, a ceramic, a glass, a soil or a liquid.

{
    "module": { "prefix": "MYMOD_", "name": "My Module", "version": "1.0" },
    "materials": [
        { "key": "GOLDBRONZE", "name": "gold bronze", "material_class": "METAL" }
    ]
}

Three fields are required: key, name, material_class. key is uppercase with no spaces. Every field:

#4.1Material classes

material_class does two things: it picks which flags your material gets, and it tells RM what kind of existing material to clone for structure.

Class Produces Capabilities
METAL Bars Weapons, armour, ammo, diggers, anvils, furniture
STONE Boulders Construction, furniture, quern stones
CERAMIC Boulders Construction, furniture, tools. No weapons or armour
GEM Rough gems Cutting, encrusting. Requires gem_names
GLASS Rough glass Construction, furniture, trap components, crafts. No weapons or armour
SOIL Boulders Clears every metal, gem, ceramic and glass flag and every item capability, then sets IS_STONE
LIQUID Nothing solid Clears the same flags and capabilities, then sets LIQUID_MISC_OTHER
DYE Powder (POWDER_MISC) A dye every dye job takes. Declare it on a plant host, not as an inorganic (see 7.2)
RAW Nothing by default No preset at all. You set every flag yourself

On GLASS: vanilla's green, clear and crystal glass are builtin material types, not inorganics, so no vanilla world holds an IS_GLASS inorganic for RM to clone. RM falls back to a ceramic donor, and the GLASS preset then clears IS_CERAMIC and sets IS_GLASS. None of that is visible in play. The material is glass.

Note that since glass is builtin, not inorganic, simply injecting a new glass material will not automatically populate the glass furnace with reactions, unlike inorganics such as smelted metals. Glass furnace reactions must be built individually the way vanilla builds glass: one reaction per material per item, at the glass furnace, taking sand straight through to the finished object. Vanilla has no green glass bar that gets worked afterwards, and your material does not need one either. The cost is volume, not difficulty: a full item range runs to roughly three dozen reactions per material.

On DYE: the preset sets IS_DYE and the two plant powder flags every vanilla dye carries, and RM writes the dye colour (powder_dye) from the material's colour, or from dye_color when you set it. Declare dyes on a plant host in your plants file (section 7.2). DF files a powder by the type of its material: an inorganic dye is either stranded where it was made (with the plant flags) or stored as an empty bag under Furniture and listed nowhere (without them). Preflight warns when a dye is declared as an inorganic.

On RAW: no flags are cleared and none are set, so whatever RM cloned carries through untouched and material_flags is your only control. It exists for cases where the presets get in the way. If you are not sure you need it, you do not.

#4.2Why "null" is not "zero"

Every optional field accepts null, and null means do not write this field. The value from RM's clone donor stays in place.

That donor is chosen at runtime by scanning the loaded world, so it can differ between worlds and between mod sets. A null density does not give you zero density. It gives you an unpredictable one.

Write real numbers. The only field where null is routinely correct is value, and only when you are computing it in Lua (section 8.3).

color is the colour that matters in the graphical game. It is a descriptor colour ID from descriptor_color_standard.txt (or another mod's descriptor raws), matched case-insensitively against the colours loaded in that world. RM writes it as the material's state colour: the colour DF tints a sprite with where it tints one, and a dye's colour unless dye_color gives another.

An ID that is not loaded fails silently. RM tries fallback_colors in order, and if none of those is loaded either, the material takes descriptor colour 7, with no error printed anywhere. fallback_colors is the only protection you get. Always supply at least one. An unloaded dye_color is logged, and the material's own colour is used instead.

display_color, build_color and tile are ASCII-mode fields: the classic display draws a material's tile in its colour, and nothing in the graphical game reads them. RM writes display_color and build_color only together with color; when color is set and they are not, RM writes a default triple.

If you use a colour ID your own raws half defines, verify it at load time. The advanced template has a color_exists helper for this.

#4.4Temperatures

heat takes seven optional numbers: spec_heat, melting_point, boiling_point, ignite_point, heatdam_point, colddam_point, mat_fixed_temp.

"heat": { "spec_heat": 450, "melting_point": 12718, "boiling_point": 14877 }

DF temperatures are in urists, not degrees. The scale is Fahrenheit offset by 9968, so 9968 U is 0 degrees F.

Reference point Urists
Water freezes and ice melts 10000
Comfortable room temperature 10036
Water boils 10180
Magma 12000

The first row is the one to anchor on: 10000 is freezing, not room temperature. Vanilla WATER carries MELTING_POINT:10000 and BOILING_POINT:10180, which is where those two numbers come from.

Magma sits at 12000, so a material needs a melting point above 12000 to survive contact with it. Vanilla iron melts at 12718 and boils at 14877; those are useful reference points for positioning a metal.

#4.5Reaction classes and reaction products

These two fields are what let materials participate in chains without anyone hardcoding anything.

reaction_classes is a list of tags. A reagent can then say "accept anything carrying tag X" instead of naming materials. This is the only supported way for modules to interact. Section 9 covers it properly.

"reaction_classes": ["THERMALLY_PROCESSED", "CALCIUM_SILICATE"]

An empty array is meaningful and worth writing: it explicitly clears anything inherited from the clone donor.

reaction_products are named derivations. They answer the question "when a reaction asks this material for product X, what does it hand back?" Each entry needs id and mat_id.

"reaction_products": [
    { "id": "FIRED_MAT", "mat_id": "MYMOD_STONEWARE" }
]

This is how vanilla fires clay. The reaction does not name any clay. It says "any boulder that declares a FIRED_MAT product", and the output says "whatever that material's FIRED_MAT is." One reaction then handles every clay in the world, including clays from mods that have never heard of it.

mat_id must be the full prefixed ID. Cross-module references are resolved in a final pass after every module has injected, so they work in either direction, including between two modules that reference each other.

#4.6Strength

strength takes three groups, yield, fracture and strain_at_yield, each with any of IMPACT, COMPRESSIVE, TENSILE, TORSION, SHEAR and BENDING, plus a single max_edge and a single absorption (how much a porous material such as clay or ceramic absorbs). Every value is a number or null.

"strength": {
    "yield":    { "IMPACT": 1505, "COMPRESSIVE": 1505 },
    "fracture": { "IMPACT": 2520, "COMPRESSIVE": 2520 },
    "max_edge": 10000
}

#4.7Graphics

graphics writes sprites into the material's own slots: bar, boulder, wood, rough, cheese and texflag. Each slot takes a source string, or a table with donor (a source string) and an optional offset (a number).

"graphics": { "boulder": "PAGE:BOULDERS:1:15", "bar": { "donor": "INORGANIC:IRON#bar" } }

A source names where an existing sprite lives:

Source Meaning
TEXPOS:<n> A literal texture position. Changes between sessions; debugging only
TOOL:<itemdef code> A tool itemdef's sprite fields
INFO:<table>:<n> An entry in one of DF's *_graphics_info tables
PAGE:<page>:<x>:<y> A cell of a loaded tile page, by the coordinates the raws use
FILE:<path>:<x>:<y>[:<width>] A cell of a PNG on disk, its path relative to your data folder (images/...). <width> is the sheet's width in tiles, for a sheet RM cannot measure on its own
BUILTIN:<material>#<slot> A builtin material's slot
INORGANIC:<id>#<slot> Any inorganic's slot
TINT:<art name> Art registered with RM's sprite art, tinted to this material's colour

A material slot does not take on the material's colour by itself: a sprite written there shows exactly as drawn. TINT: is how a material gets art in its own colour; the art is registered from Lua with refinish-sprite-art.

#5The reactions file

A reaction is one job: what it consumes, what it makes, where it appears, who can do it.

{
    "module": { "prefix": "MYMOD_", "name": "My Module", "version": "1.0" },
    "categories": [ ... ],
    "reactions": [ ... ]
}

#5.1Reaction fields

Field Required Notes
key Yes Unique in this file. Gets the prefix.
name Yes What the player reads. Lowercase, verb first.
building Yes Where the job appears (section 5.2).
skill No, but set it What the worker trains (section 5.3).
fuel No Default false. True makes the job burn fuel; magma buildings are exempt.
category No The full prefixed category ID.
description No Text shown in the task pane under the job's Produces and Requires lines. A string is one entry; an array is one entry per element.
building_hotkey No The job's hotkey at its building, as a df.interface_key name. An unknown name is logged.
permissions No Default AUTO. Which civilizations get it (section 5.5).
reaction_flags No Currently just fortress_mode.
fallback_template No Override RM's structural donor choice.
reagents Yes At least one. Codes must be unique within the reaction.
products Yes At least one.

Always set skill. RM builds a reaction by cloning an existing one for its C++ structure, then zeroing every semantic field and rebuilding from your definition. If you omit skill, the donor's skill survives, and which donor got picked is not something you control.

fallback_template exists to override that donor choice by naming a vanilla reaction code. You almost certainly do not need it. The neutral reset means a suboptimal donor is a cosmetic issue, not a functional one.

#5.4Categories

Categories are the collapsible headings in a workshop's job list. Optional.

#5.5Permissions

Permissions decide which civilizations know the reaction. This affects what caravans bring, what invaders carry, and what other sites produce. It is not about your fortress.

AUTO (the default) evaluates every civilization and grants the reaction to any that can operate the building (its capability gate in BUILDING_CAPABILITY_GATES) and knows the metals the reaction works. A civ that cannot smelt does not receive smelting reactions. This is right for ordinary content.

"permissions": { "mode": "AUTO" }

ENTITY_CODE grants only to the entity codes you name, in a non-empty entities array. The same capability gate still applies on top, so naming a civ that cannot use the building does not force it through. Codes are whatever is loaded, vanilla or modded. entities is refused with any other mode.

"permissions": { "mode": "ENTITY_CODE", "entities": ["MOUNTAIN", "PLAINS"] }

NONE grants to nobody.

"permissions": { "mode": "NONE" },
"reaction_flags": { "fortress_mode": true }

fortress_mode is easy to read backwards. It is a bypass, not a restriction. True means the player's own civilization type can run the reaction without an explicit permit. Combined with NONE, the result is a recipe the player has and no other off-type civilization does, so it never shows up in off-type caravan stock or on a goblin's back.

Default is false, meaning the player needs a permit like everyone else.

Your buildings and tools need no permissions written: RM permits every building definition carrying your prefix to every civilization, so it appears in the build menu, and gives your tools to the fort's civilization.

#6Reagents and products in depth

#6.1Codes are local, material IDs are global

A reagent's code is a private label inside one reaction. It is how products and container links point back at a slot. It never leaves the reaction and never takes a prefix. Lowercase by convention. Two reagents in one reaction may not share a code.

Anywhere you write mat_id or metal_id, you are naming a real loaded inorganic. Vanilla materials use their bare ID (IRON, GYPSUM, QUICKLIME). Module materials use the full prefixed ID (MYMOD_GOLDBRONZE). mat_token names any material by its full token (section 6.9).

#6.4The container pattern

Powders and liquids always travel in something, so they are always two reagents. Which flags go where depends on direction.

Output into a container. The bag is preserved and must be empty; the product names it.

"reagents": [
    { "code": "limestone", "type": "FLUX", "quantity": 2 },
    { "code": "bag", "type": "BAG", "quantity": 1,
      "flags": { "preserve": true, "empty": true } }
],
"products": [
    { "type": "POWDER_MISC", "mat_id": "MYMOD_LIME", "count": 4,
      "dimension": 150, "to_container": "bag" }
]

Input from a container. The powder is in_container; the bag is preserved and contains the powder.

"reagents": [
    { "code": "lime", "type": "POWDER", "mat_id": "MYMOD_LIME",
      "quantity": 150, "flags": { "in_container": true } },
    { "code": "bag", "type": "BAG", "quantity": 1,
      "flags": { "preserve": true }, "contains": "lime" }
]

Read the pairing as: the bag contains the powder, the powder is in a container. Put contains on the container, pointing at the contents. A contains naming a code the reaction does not have is refused.

A hard limit: one slot must be satisfied by the contents of one bag alone. DF will not aggregate several bags to fill a single slot. If you need four bags' worth, that is four reagent slots.

#6.5The four ways a product picks its material

Exactly one. Not zero, not two.

mat_id names an inorganic output directly.

{ "type": "BAR", "mat_id": "MYMOD_GOLDBRONZE", "count": 4 }

mat_token names any material by its token, plant materials included (section 6.9).

get_material_same copies the material of a reagent item straight through. The knapping pattern: the sharp rock is made of whatever rock was knapped.

{ "type": "ROCK", "get_material_same": "stone", "count": 2, "force_edge": true }

get_material_product asks a reagent's material what it derives into, using a product code that material declared (section 4.5). Both reagent_code and product_code are required. This is the strongest of the four, and the one most worth learning.

"reagents": [
    { "code": "clay", "type": "BOULDER_ANY", "quantity": 1,
      "has_material_reaction_product": "FIRED_MAT" }
],
"products": [
    { "type": "BOULDER",
      "get_material_product": { "reagent_code": "clay", "product_code": "FIRED_MAT" },
      "count": 1, "dimension": 600 }
]

Nothing here names a clay. The reagent accepts anything that knows how to be fired, and the product asks that same material what it fires into. One reaction, every clay in the world, including ones added after you shipped.

When a reagent slot holds several materials, RM shares a get_material_same or get_material_product output over the materials that slot actually held, by volume, instead of making it all in the first item's material. That holds for every custom reaction.

#6.8The magnifying glass

The magnifying glass icon lets the player choose which specific material a job uses. It appears for BAR, BLOCKS, BOULDER, ROUGH, and SMALLGEM reagents when the material is left as any inorganic. BOULDER_ANY is built for exactly this.

It does not appear for POWDER_MISC, in any configuration, and a TOOL reagent gets none either. That is a DF engine limit, not something runtime injection can work around. If your design needs the player to pick the material of a powder or a tool, it needs one reaction per material.

#6.9One more trap: economic stone

BOULDER_ANY with flags.non_economic grabs every non-economic inorganic in the world, and that includes processed materials your own module produced. A grinding reaction meant for raw stone will happily eat your finished output.

The fix is to give processed materials a reaction_class. Carrying one makes a material economic, which takes it out of the non_economic net.

#6.10Naming any material: mat_token

mat_id names an inorganic only. mat_token names any material by its full token, the way the raws do, and it works on reagents as well as products:

{ "code": "log", "type": "WOOD", "quantity": 1,
  "mat_token": "PLANT_MAT:ACACIA:WOOD" }

{ "type": "POWDER_MISC", "mat_token": "PLANT_MAT:MYMOD_DYE_HOST:MY_DYE",
  "to_container": "bag", "count": 1, "dimension": 150 }

A material on your own host plant is PLANT_MAT:<prefix + plant key>:<material key>. Preflight checks those against your plants file; tokens for vanilla or another mod's plants resolve when the reaction is built.

A reagent token that does not resolve closes the slot: the reagent is given a reaction class no material carries, so the reaction shows and cannot run, and the log names the token. It never falls back to "any material", which would let a slot meant for one tree's logs take every log in the fort. Give a token or a mat_id, not both; if both are there, the token wins and the log says so.

#8The advanced Lua shell

The basic template hands RM two file paths. That is correct whenever your JSON is complete on disk and nothing in it depends on the world that just loaded.

The advanced template loads the JSON itself, edits the parsed tables in memory, and hands RM finished data. Use it when you need to ask a question your JSON cannot answer, start helper scripts, or ship tools, plants or buildings:

  • Which sand does this world have?
  • Is my raws half actually installed?
  • What should this alloy be worth, given local metal prices?

Every system in that template is independent. Delete what you do not need.

#8.1The listener contract

Register once, at load, with register_listener(name, callback, mod_id) on refinish-module-engine. Both templates do this for you (register_with_rm in the advanced one).

MODULE_ID is your info.txt ID. With it, RM only calls your listener in worlds where your mod is active. Without it, your listener is called in every world.

RM calls your listener once per startup, after world raws are loaded, before injection. Return a table holding any of:

Key What it is
materials_json, reactions_json, tools_json, plants_json, buildings_json Paths to your JSON files
materials, reactions, categories, tools, plants, buildings Finished tables instead of paths, alongside a module block on the same table
module The module block, for finished tables
buildings_dir With finished buildings: the folder their image paths are relative to
data_dir With no JSON path to take it from: the folder FILE: sprite sources are relative to

         start = start_helpers, stop = stop_helpers }

A file that will not parse refuses the module. A listener that errors, or returns nothing, refuses it too, and the log says which; the usual cause of nothing is a MODULE_ID that does not match info.txt, which leaves the module unable to find its own folder. Return nothing on any failure that would otherwise inject partial content.

#8.2Raw dependency checks

Injection is forgiving in the worst possible way. A missing material resolves to index -1 and the reaction silently accepts nothing. A missing colour resolves to grey. The player gets a half-working mod and no way to find out why.

The template has three checks: inorganic_exists, color_exists, workshop_exists, run by check_raw_dependencies. Fill in the lists, and a missing dependency becomes one clear message instead of a mystery.

Two notes on how to use them:

  • Pick sentinels, not exhaustive lists. One material that only your raws half defines proves the whole file loaded. Checking all twenty-six just makes a longer message.
  • Report, do not gate. A missing dependency degrades the module; it does not disable it. Say what is wrong and load anyway.

#8.3Computing values

A hardcoded alloy value is a guess about a world you have not seen. Metal prices shift with the mods installed, and an alloy priced against vanilla iron can end up worth less than its own ingredients.

"value": null,
"value_from_reaction": "MAKE_GOLDBRONZE"

value_from_reaction is not part of RM's schema. RM ignores unknown fields, so it passes through untouched and your Lua file reads it. The template's calculate_weighted_value averages the live material values of the reaction's BAR reagents, weighted by quantity.

#8.4Resolving materials at runtime

Sand is the standard case. Vanilla ships five sand materials and mods add or remove more, so your JSON cannot name one. But it cannot leave the slot as a wildcard either: a POWDER reagent with no material matches any powder in a bag, and once two such slots sit in one reaction, DF has nothing to tell them apart and reagent matching goes non-deterministic.

The pattern:

  1. Write "mat_id": null as a sentinel meaning "resolve at load time."
  2. Scan the live raws for something matching a property, such as the SOIL_SAND flag.
  3. Write the real ID into the parsed table before returning it.
  4. If nothing matches, remove the affected content so the module degrades cleanly instead of injecting jobs that can never start.

The engine never sees the null.

Nothing in resolve_target_id is sand-specific except the flag it tests. Swap that test and reuse the shape.

#8.5Helper scripts

Some things the schema cannot express: injecting a button into a workshop's order list, hooking job completion, fixing up created items. Those go in companion scripts exposing start() and stop(), listed in HELPER_SCRIPTS.

The template returns start = start_helpers and stop = stop_helpers. RM runs start only once your module is accepted and injected, and runs stop before every save, at a shutdown and at the map unload, before your assets leave RAM. So no helper outlives the data it reads, and a module RM refuses starts nothing. You need no map unload hook of your own.

Never start a script from the listener itself: it runs before validation, and before your data is in RAM.

#9Working with other modules

#The rule

Avoid direct reference to another module's material by mat_id.

If that module is not installed, your reagent resolves to nothing and the reaction silently accepts no input. The player sees a job that never starts.

#The mechanism

Modules interact best through shared reaction_class tags.

A material opts in by carrying a tag:

{
    "key": "SLAG",
    "reaction_classes": ["THERMALLY_PROCESSED", "BYPRODUCT"]
}

A reaction anywhere asks for the tag, not the material:

{
    "code": "slag",
    "type": "BOULDER_UNTYPED",
    "quantity": 3,
    "reaction_class": "THERMALLY_PROCESSED"
}

Neither side knows the other exists. If the producing module is not installed, the reaction simply finds no input; it does not break. If three modules produce tagged materials, all three feed the same reaction.

Name tags after the process, not after your material. THERMALLY_PROCESSED invites participation. MYMOD_SLAG does not.

#depends_on

When you genuinely must name another module's material, declare it:

"module": {
    "prefix": "MYNEWMOD_",
    "name": "My New Module",
    "version": "1.0",
    "depends_on": ["MYOLDMOD_"]
}

Each entry is a prefix ending in an underscore, and not your own. RM injects the named modules first. A module whose dependency is missing is skipped, and the log names what it needed. This is for reaction_products links and similar hard references, not a substitute for reaction classes.

Cross-module reaction_products are resolved in a final pass after every module has injected, so they work in either direction, including mutual references.

#RM's catalog: requires

RM carries a catalog of general item forms that any module may use: dust (REFINISH_CORE_DUST, always present) and forms injected only when an accepted module asks for them, each a tool named REFINISH_<FORM>_TOOL:

  • GRAVEL, with its crush reactions at the mason's workshop and the stone aggregate twins (REFINISH_CORE_AGG_<stone>) that carry the AGGREGATE class;
  • the byproduct forms SAWDUST, BARK, SCRAP, CULLET and CRUST (with its gall material);
  • HEAP, a bar sized heap (600) for loose bulk, carrying the slag material: while it is injected RM pays an ore smelt's whole loss as slag heaps, and recipes take slag by AGGREGATE or SLAG.

A form is a hollow item type; what it is comes from the material you put on it. Ask for one rather than defining your own, so players never carry two of the same thing. The catalog holds only content many modules can use: anything that only makes sense inside your module stays in your module.

Reaction keys (refinish-reaction-keys) are the exception to sharing: give your keys a tool of your own, because a watcher sweeps its key tool by subtype and removes keys it does not recognise.

Ask for the forms you use in any of your module blocks:

"module": {
    "prefix": "MYMOD_",
    "name": "My Module",
    "version": "1.0",
    "requires": ["GRAVEL", "SAWDUST"]
}

RM injects every requested form before your module, so your reactions can name REFINISH_SAWDUST_TOOL as a tool_id. A name that is not in the catalog this session is logged as an error naming your module, and your module runs without it.

If your module is a Lua listener returning one table, put requires in that table's module block, or gather it there from your other files' blocks (see how making_fuel.lua does it).

#10Troubleshooting

#Module never appears in the log

The listener never registered or never returned. Check in order:

  • Is the Lua file in scripts_modinstalled/?
  • Does MODULE_ID exactly match [ID:...] in info.txt? A mismatch makes the path lookup fail, and, when passed as mod_id, the log warns that it matches no installed mod.
  • Is RM itself installed and enabled?

#"Rejected", "Omitted" and "left out"

RM checks your materials, reactions, categories and tools one entry at a time. A bad entry is omitted and named, and the rest of your module still runs. A reaction that names an omitted material (by mat_id or an INORGANIC: mat_token), or names an omitted tool as a product subtype, is omitted with it.

The module is rejected whole when its listener errors or returns nothing, when a JSON file will not parse, when its materials or reactions module block is invalid, when nothing valid is left in its materials or reactions, when the materials and reactions prefixes differ, when no file carries a prefix, or when its prefix overlaps another module's or REFINISH_STEEL_.

The message names the exact field. Common causes:

  • module.prefix does not end in an underscore.
  • The materials and reactions prefixes differ.
  • A material or tool key has lowercase letters or a space.
  • A material_class of GEM with no gem_names.
  • A product with zero or two material sources.
  • A contains naming a reagent code that does not exist.
  • A reagent type that no longer exists (section 6.3, renamed in v4).

#"prefix overlaps"

Another module's prefix is a stem of yours or vice versa. Rename.

#Material is the wrong colour

color names a descriptor colour ID that is not loaded in this world, and no fallback_colors entry is loaded either, so RM used descriptor colour 7. Add fallback_colors, and add a color_exists check so it stops being silent.

#Reaction appears but never starts

Almost always a reagent that matches nothing:

  • A mat_id naming a material that does not exist. Check with refinish-find.
  • A mat_token that did not resolve: the log names it, and the slot is closed.
  • A container slot needing more than one bag's contents.
  • A reaction_class no loaded material carries.
  • Conflicting filters, such as a mat_id and sand_bearing on the same slot.

#Reaction does not appear at all

  • It was omitted: the log says why.
  • The category is not the full prefixed ID.
  • The building is a custom workshop that is not installed.
  • Permissions excluded the player's civilization, and fortress_mode is false.

#Reaction eats the wrong thing

A BOULDER_ANY with non_economic is catching your own processed materials. Give those a reaction_class (section 6.9).

#Diagnostics

  • preflight.py catches schema and reference problems before you launch DF. Run it first; it is faster than any in-game test.
  • refinish-find locates injected content in memory.
  • refinish-path traces how something was built.
  • RM's log panel records every injection decision, including which structural template each reaction cloned. Set Log Detail to Debug to see all of it.

#11Rules and conventions

#Hard rules

  1. Never reference another module's material by mat_id without declaring depends_on. Use reaction classes.
  2. Your prefix must not overlap anyone else's, in either direction, nor RM's own.
  3. Verify vanilla assets you depend on. Another mod may have cut them.
  4. Start your scripts in start and stop them in stop, never from the listener.

#Naming

  • Material, tool, plant and building keys: uppercase, underscores, no spaces. Descriptive of the thing, not the process. GOLDBRONZE, not ALLOY_3.
  • Reaction keys: uppercase, verb first. MAKE_GOLDBRONZE, GRIND_CEMENT.
  • Reaction names: lowercase, verb first, the way vanilla phrases it. make gold bronze bars.
  • Reagent codes: lowercase, local, descriptive. copper_bar, sand_bag_1.

#Content

  • Set skill on every reaction.
  • Set real numbers rather than leaving nulls, except where you compute them.
  • Always supply fallback_colors.
  • Give processed materials a reaction_class, both for interoperation and to keep them out of non_economic filters.
  • Put non_artifact on every reagent that consumes a wildcard input.
